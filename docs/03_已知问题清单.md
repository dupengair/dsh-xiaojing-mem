# 03 · 已知问题清单（dsh-fish-memory 排雷记录）

> 读参考实现时发现的坑、修过的问题、以及我们自己实现「小鯨记忆」时要按图排雷的清单。每条尽量给源码定位或版本依据。持续追加。

## A. 插件自身已知的坑（源码/注释里实锤）

### A1. trace 重复记录（v1.5.2 已修，老库里仍有残留）
- 现象：工作区 json 里同一句话连着好几条 trace。
- 根因一：同一次请求里装配函数被调两遍，各 push 一条；实测 222 条里 108 条是"同句相隔 3 秒内"的重复。修复：同 query 且 <3000ms 覆盖（lib/index.js:4478-4500）。
- 根因二：工作区模式多会话轮流写 trace，天然像重复——不是 bug，是日志本来就按"每次回忆"记。
- **排雷**：日志和记忆本体分开；日志去重按"同 query + 短时间窗覆盖"；记忆本体去重按语义/事实键。
- 排雷项：日志去重按"同 query + 时间窗"；记忆本体去重按语义/事实键。

### A2. 卸载函数两层错，开关"关了照样注入"（2026-09-21 修）
- DSH 的 `systemPrompt.section()/context()`/`tools.register()` 返回的是**函数**（Cordis disposer），不是 `{off()}` 对象——`typeof x.off === 'function'` 永远不成立，一次都没卸掉过。
- `mountFor` 原返回 `{off(){}}` 对象，调用方 `v.off()` 拿对象当函数调 → TypeError 被 try/catch 吃掉，静默无效。
- 结果：开关关了注册还活着；再开又因 already registered 每 3 秒失败。
- **排雷**：我们自己的挂载/卸载必须跟随宿主约定——disposer 是函数就直接调；每个挂载点都要写"关→验证立刻停注入"的测试。

### A3. section 注入打穿前缀缓存（20 倍成本）
- 把每轮变化的记忆拼进系统提示词：缓存读取 11,392 → 0，单轮成本 0.001 → 0.02。
- **排雷**：常量进系统提示词（section，order 排到宿主所有段之后），每轮变化的走 `context`（对话末尾追加、变了才追加）+ 同 query 短时缓存（参考：1.5 秒，实测 text() 一轮被调 3~24 遍）。

### A4. 模板变量炸整条会话
- 宿主默认对注入文本做 `{{var}}` 替换；记忆里存了带双花括号的代码片段 → `unknown prompt variable` → 该会话每轮失败，用户只能关插件。
- **排雷**：所有注入文本 `interpolate: false`；入库文本不做任何转义假设。

### A5. DSH 时序：装配时拿到的"最后一句用户消息"是上一轮的
- `systemPrompt.context` 在请求装配时求值，user 消息装配完才落 session → 拿 `lastUserText` 检索永远晚一轮（实测问"莱拉是谁"，搜的是上轮闲聊）。
- 修复：用 `agent/inbox/inserted` 监听句优先（mountFor，lib/index.js:4277），lastUserText 只兜底。
- **排雷**：检索 query 必须来自"本轮真实输入"事件，不信装配时刻的 session 状态。

### A6. 注入泄漏：上轮注入被当成本轮线索
- 上一轮的【你记得的事】留在对话里，下一轮检索把它当 query 的一部分，滚雪球。
- 修复：清掉注入上下文（lib/index.js:2165）剥掉宿主注入块。
- **排雷**：检索前必须剥自己注入的内容。

### A7. "没挑中"分支判错，自动扩词 20 句后永不触发
- `gate` 放行时也是个对象（记着信息量），`if (!gate)` 永假 → 补词分支死路。
- **排雷**：判"被门挡了"要看 `gate.挡了` 这类显式标记，不要对对象取非；每个分支写真实用例测试，防"看起来能跑其实永远不进"。

### A8. 并发写丢记忆（已修）
- 自动扩词等模型返回的几秒里，别的会话新记的记忆被旧快照覆盖。
- 修复：saveStore 写前读盘按 id 合并（lib/index.js:620，lib/store-merge.mjs）+ 原子写 + 损坏备份 + purgeEpoch 防复活。
- **排雷**：任何异步路径（等模型、后台任务）持库超过一瞬，写回前必须重新合并；不要长持内存快照。

### A9. 重复 trace 白占一半日志
- traces 上限 100，重复占掉一半 → 有效日志只剩 50 轮。
- **排雷**：日志去重要和上限一起设计，否则上限形同虚设。

## B. 设计取舍（照抄前先想清楚）

### B1. 无自动提炼/晋升
- 只有 stable_profile / event 两层，写入瞬间定层，无短期→长期晋升管线。"重新认识"靠 生成档案.js 离线批量造库。
- **待议**：我们是否要补"夜间沉淀"（把高复访 event 归纳成 profile）——这正是 3d-memory-sea 的 confirmed 字段思路，可作为我们的差异点。

### B2. 遗忘只是排序后退，永不下架
- 好处：可逆、手感像人；代价：库只增不减，靠 dailyQuota 限流兜底。
- **待议**：我们要不要加"归档层"（如 N 个月未被召回且低重要 → 移入冷存储，可恢复不参与检索）。

### B3. 无导入导出 UI，无画像文件
- "认知"=散条记忆，无结构化画像；迁移=拷目录。
- **待议**：我们的展示机制（记忆星图）天然需要结构化视图，可顺带做导出。

### B4. 用上了 = 实词重合的猜测
- assembled→consumed 靠回复与记忆文本的实词重合，是猜测不是事实（设置页也只敢写"像是用上了"）。
- **排雷**：我们做"记忆使用率"统计时要继承这个不确定性措辞，别把猜测当指标承诺。

## C. 环境与工程（本项目自带，非插件问题）

- 沙箱内 `git push` 需 danger-full-access（msys 子进程无法建信号管道/credential helper 崩）；直连 TLS 断（SSL_ERROR_SYSCALL），走 `git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push`。
- 参考 clone（dsh-fish-memory/、3d-memory-sea/）只读，已被 .gitignore 白名单排除，不入库。
- 真实记忆数据（含小主的 fish-memory json）不入库。
