# 05 业界记忆方案调研：结构化索引用于 Agent 用户记忆的现状与二期选型

> 背景（2026-11-13）：小主问——业界有没有把结构化索引用来做 Agent 用户记忆？二期有必要上结构化索引吗（如 RAPTOR、GraphRAG）？
> 本文为调研结论全文，供需求/设计文档引用。

## 一、业界现状：三条路线

### ① 时序知识图谱（Temporal Knowledge Graph）——最接近"用户记忆"的结构化路线

代表：**Zep / Graphiti**（[github.com/getzep/graphiti](https://github.com/getzep/graphiti)）。

- 每条记忆（episode）分解为**实体（节点）+ 关系（边）+ 时间属性**；每条边带 `valid_from` / `valid_to` / `invalid_at` 有效期窗口——事实有"何时成立、何时被取代"。
- 双时间模型：区分**事实生效时间（valid_time）**与**系统记录时间（recorded_at）**，能回答"某时刻为真吗""搬家前地址是什么"。
- 独立评测（LongMemEval，[arXiv:2603.04814](https://arxiv.org/abs/2603.04814)）：Zep 63.8%（GPT-4o）。强项：多跳关系、时序推理、知识更新类问题。
- ⭐ **与我们设计的关系**：Graphiti 的有效期模型 + `supersedes` 取代链，与我们的「事实键 + 被取代」机制是同一思想。我们的方向没跑偏，往前半步就是双时间戳。

### ② 向量 + 图双库路线

代表：**Mem0**（[mem0.ai](https://mem0.ai)）。

- 双库架构：语义检索走向量库，实体关系走图库；写入时同时做嵌入和实体关系抽取。
- LongMemEval 独立评测 49.0%。简单偏好/个性化查询够用；多跳、结构推理弱。图能力锁在 Pro 付费档。
- 优势：Apache 2.0 完全可自托管、生态最大（~48K stars）。

### ③ RAPTOR 式层级摘要——本质是"索引阶段提炼"的结构化

- [RAPTOR](https://scholar.google.fr/citations?view_op=view_citation&hl=fr&user=uyFDSDwAAAAJ&sortby=pubdate&citation_for_view=uyFDSDwAAAAJ:blknAaTinKu)（Recursive Abstractive Processing for Tree-Organized Retrieval）：对文档**递归聚类 + 摘要**，建"越往上越抽象"的树；检索时树上任意层可命中——细节问题打叶子，概括问题打上层节点。
- 原本为文档 RAG 设计，但其"把个案逐级压缩成统计摘要"正是黑猫白猫计数问题（docs/04 Q4）的业界解法。
- 业界综述（[Agent Memory Technical Overview](https://raw.githubusercontent.com/runzhliu/aik8s/refs/heads/main/translations/en/ai-k8s/rag-agent/agent-memory-technology-overview.md)）对 consolidation 的描述与它同构：repeated preferences 合并成带证据计数的 Profile、任务轨迹蒸馏成"问题—动作—结果—适用条件"的案例、旧会话逐级摘要并保留回链原始事件。
- 相关佐证：**Hindsight** 四路并行检索（语义 + BM25 + 图遍历 + 时序推理）+ cross-encoder 重排，LongMemEval 94.6%——证明**多路混合召回**优于押注单条通道。

## 二、二期要不要上？结论：**不上重型结构化索引引擎，把"结构化"落在三处便宜的地方。**

**判断依据（我们的规模与数据形态）**：

- 个人记忆、单主体、量级千~万条；无跨实体多跳查询的真实需求。
- 图数据库（Neo4j 等）建模与运维成本实打实；综述明确建议"先 PostgreSQL+pgvector 把治理做对，关系和多跳真正成为瓶颈再上图"。
- 结构化索引的价值大头在 **schema 设计与提炼产物**，不在引入图数据库本身。

**二期落法（四件套）**：

1. **schema 层抄 Graphiti**：每条记忆带 `valid_time(from/to)` + `recorded_at` + `supersedes` + `source` 溯源。事实键取代机制往前半步即双时间模型，成本近零。
2. **沉淀层抄 RAPTOR 思想（不抄树引擎）**：周期性把 event 层聚类提炼为"摘要层"条目——统计摘要 / 边界规则 / 画像更新（见 docs/04 Q4），条目带 `derivedFrom` 回链原始个案。树不真建，先两层（个案层 + 提炼层），量大了再加中间层。
3. **混合召回**：词面（现有）→ 向量（sqlite-vec，03 清单 D1/B5）→ 必要时图边（内容机制侧），多路并行 + 合并排序。
4. **图留给内容机制**：Obsidian 笔记天然带双链（实体关系），sidecar 建实体边顺手；私人记忆库不上图。真出现多跳需求再评估图存储。

**一句话**：业界已验证方向——结构化索引确是大势，但赢在 schema 与提炼产物，不是赢在图数据库。二期用「双时间戳 + 溯源 + 两级提炼 + 混合召回」吃到 RAPTOR/Graphiti 八成收益，付一成成本。
