## 小主的五组问题（原文要点）

1. **记忆与会话的匹配方式**：按工作区和按会话两种方式实现有何不同？单个会话分别保存，还是工作区下所有会话合在一起？
2. **权重管理**：基础、鲜活度、情绪权重怎么起作用、怎么判断大小、怎么记录保存？单次对话 vs 整个会话两种场景下三者的作用有何差异？这个机制怎样决定什么容易被想起来？
3. **遗忘**：半衰期与情绪半衰期有什么不同？怎么影响一个会话？
4. **记忆提炼与保存、注入**：记忆怎么提炼、如何压缩？触发点按时间周期还是内容多少？有没有短期/长期多层记忆？上下文满时怎么处理、会触发保存吗（DSH 压缩上下文前是否需要先保存）？保存格式是 md 还是结构化数据、存哪里？注入时怎么选、怎么选取要注入的部分？
5. **导入导出**：设置界面似乎没有导入导出——换电脑/重装插件、DSH 后记忆文件是不是就没了？

## 1. 记忆与会话的匹配方式

核心实现：`lib/index.js:294 storePath()`、`lib/index.js:432 库名()`。

- **按会话（默认，`模式: 'session'`）**：每个会话一个独立库 `~/.dsh/fish-memory/<会话id>.json`，互不可见。
- **按工作区（`模式: 'workspace'`，v1.4.5 加入）**：同一工作区所有会话在最底层映射到**同一个文件** `ws_<工作区id>.json` —— 不是事后合并，是从源头共用一份库。归档旧会话不带走记忆，新会话一开自动接上。
- 两种模式**二选一**（同时开 = 一份记忆被两套归属抢，必出 bug）。配置读不到 / 工作区算不出时退回按会话，"绝不因为算不出就把记忆弄丢"。

## 2. 权重管理

参数定义：`lib/index.js:143 DEFAULT_POLICY`；评分：`lib/index.js:3075 evaluate()`。

```
P = C × (baselineWeight + activationWeight×A + importanceWeight×I + emotionWeight×E)
```

- **C（证据）**：问句命中的词在这条记忆里的"稀有度"（IDF，`lib/index.js:2845 稀有度()`）之和，再过 `C = s/(s+K)` 归一化（K = `rarityK`）。每个词还乘"她自己的说话稀有度"——天天挂嘴边的词几乎不算证据。撞上扩词全价、干净碎片片价、只撞正文打折。
- **A（鲜活度）**：`A0 × 2^(-天数/H)`（`lib/index.js:3048 鲜活度()`），从强化锚点起算；被再次提到时 `A' = A + 0.2×(1-A)` 强化（`at` 不动）。
- **I（重要度）**：写记忆时标 0~1；同时**拉长半衰期**：`H = baseHalfLifeDays × (1 + 2×I)`。
- **E（情绪）**：`emotion × 2^(-天数/emotionHalfLifeDays)`，比事实淡得快。

权重保存与范围：四项权重强制合计 100%，`fitWeights()`（lib/index.js:195）自动调平（pin 机制：用户刚改的那项钉住，其余让位）；参数各有 min/max（`POLICY_SPEC`，lib/index.js:169），防调坏。

**决定"什么容易被想起来"的关键设计**：门槛只卡 C（证据），A/I/E 只参与排序（`recall()` 里 `C < policy.threshold` 才挡）。历史上门槛卡总分 P 时，压低鲜活度会把整个库分数整体下移、连该想起的也挡掉；分离后实测"没写时间的算多鲜活"旋钮扫一遍，该想起的 11/13 一动不动。

**单次对话 vs 整会话差异**：没有会话级聚合，每条记忆独立打分逐条进；"整库级"的只有 IDF 词频表（库越大稀有度越准）和每天配额 `dailyQuota`（默认 8 条）。

## 3. 遗忘：半衰期 vs 情绪半衰期

- `baseHalfLifeDays`（默认 30，15~60）：普通记忆鲜活度 A 每 N 天减半；重要度放大它（I=1 时半衰期 ×3，重要的事忘得慢）。
- `emotionHalfLifeDays`（默认 7，3.5~14）：只管情绪分量 E，"激动劲儿先过去，事情留得久"。
- **遗忘不删除**：衰减只把排序往后推，词对得上照样召回。真要"不再想起来"走「已被取代」/「跳过」标记（`recall` 过滤 `refinedSkip` 和 `已被取代`），数据保留、可撤销。
- 没写时间的记忆：从"记下的那天"起算衰减（不知道事情哪天发生，但知道哪天记下的）；长期事实 `stable_profile` 钉在常数上不衰减。

## 4. 提炼、保存、注入

- **记忆怎么来**：**没有自动提炼/周期触发**。常规入口唯一——`remember` 工具（`lib/index.js:3629`），模型对话中自己调，一条一件事，带 importance/tags/取代/事实键。另有 `lib/生成档案.js`：离线工具，解 DSH 会话落盘文件（session.v4.jsonl.zstd，zstd 帧内 jsonl）、抽"真正说过的话"、跨会话去重后批量造记忆——用于一次性导入存量对话。
- **多层记忆**：只有两档 `category`——`stable_profile`（importance≥1，记一辈子，不衰减）与 `event`。没有短期/长期两层，"长期感"靠半衰期+重要度连续衰减涌现。
- **上下文压缩与保存的关系**：DSH 的上下文压缩**不会**触发保存，也不需要"压缩前抢救"——记忆靠模型当场记，压缩丢的只是上下文原文，库里已记的不受影响。这个插件对宿主压缩的防御是**检索侧**的：`清掉注入上下文()`（lib/index.js:2165）把宿主注入块（【你记得的事】、Current runtime context 等）从检索词里剥掉，防止"拿上一轮的注入当这一轮的线索"。
- **保存格式**：**JSON**（`JSON.stringify(data, null, 2)`），存 `~/.dsh/fish-memory/<库>.json`。结构 `{version, purgeEpoch, policy, memories[], traces[], deleted[]}`；单条字段 `id/text/at/createdAt/category/importance/emotion/tags/activation0/activationAnchor/事实键/已被取代/…`。写入：原子写 `writeFileAtomicSync` + 写前读盘合并（`saveStore`，lib/index.js:620，防旧快照静默覆盖）+ 損坏备份（`backupCorruptStore`）+ purgeEpoch 代际防"销毁后旧快照复活"。
- **注入流程**：每轮取"这一轮她真正说的话"（`挑这一轮的真话()`，`不是人说的话()` 过滤机器来源）→ `recall()`（lib/index.js:3357）：问句信息量门槛 `queryGate`（太没内容不翻记忆）→ 只拿"库里稀有的词"算证据 → 逐条 `evaluate` → 门槛卡 C → 去重（像度 ≥ 0.8 留分高的）→ 名额分档（最高 C ≥0.6→maxItems，≥0.5→4 条，≥0.4→3 条，否则 1 条，不硬凑）→ 整轮全空时从"够门槛 75%"里补一条 → `render()`（lib/index.js:3595）拼「【你记得的事】」块注入，带相对时间（"3 天前：…"），注入前再换一次人称。字数上限 `maxChars`（默认 800）。
- **检索词扩展（扩词）**：记完一条后台排队调 LLM 生成同义/场景词（每条 ≤8 个，提示词 `lib/index.js:1418 扩词系统`），离线补好，检索零在线调用。
- **同键收敛**：`按键收敛()`（lib/index.js:3294）——同一个"事实键"只留最新一条，旧的标「已被取代」；分不出新旧就不动（宁可漏标不乱埋）。

## 5. 导入导出

- 设置界面确实**没有一键导入/导出**。但不至于"换机全丢"：
  - 所有库是 `~/.dsh/fish-memory/*.json` 纯文件，**拷这个目录 = 完整迁移**；
  - 插件自带保底：`.bak`（上一版）+ `fish-memory-backup/<日期>/`（每天一份留 14 天）+ `fish-memory/销毁前/`（真销毁前另存留 20 份）；
  - 设置页有"复制到其他会话"（会话/工作区间搬运）与生成档案的存量导入路。
  - **重装插件/DSH 不删数据**（库在 DSH_HOME 不在插件目录）；真正会丢的只有"整台机器没备份 ~/.dsh"。

## 给小鯨记忆的启发

1. **门槛卡证据、鲜活度只管排序**——两件事分离，调参互不误伤，值得直接抄。
2. **衰减 ≠ 删除、取代 ≠ 销毁**：库永远可逆，设置页可见可撤销。
3. **重要度拉长半衰期**（`H×(1+2I)`）比单纯加分更优雅：重要的事自然"忘得慢"。
4. 它是**词频/全文检索，没有向量**：简单可靠零依赖，但语义召回弱。小鯨记忆可考虑：fish-memory 这套做热路径（零成本、可解释），embedding 做冷路径补充。
5. 写库安全工程值得学：原子写、写前合并、损坏备份、代际校验——记忆这种"丢了就真丢了"的数据，这些不是过度设计。
