## Q1 注入的记忆落在 system prompt 还是 user prompt？　`tag: 会话` `tag: 消息` `tag: 注入` `tag: 缓存`

**问题**（2026-11-12，小主问）：每一轮对话前被注入的记忆，是在系统提示词（system prompt）里，还是用户提示词（user prompt）里？比如 OpenAI 规范的：

```json
messages = [
  {"role":"system","content":""},
  {"role":"user",  "content":""}
]
```

**结论**：**两种位置都可能出现，但语义上永远是 system，从来不会变成 user。** 准确地说：DSH 不是「一个 system + N 个 user/assistant」的经典结构，而是把系统提示词拆成一串「系统节点」放进消息历史。查证自 DSH 实现（app.asar 内 `dsh-agent-loop` 的提示词装配与 `SystemPromptUpdate` 类型，2026-11-12）：

1. **头部（节点 0）**：系统提示词的主体（人格、工具说明、常驻 section，如 fish-memory 的【记忆】提醒 order 89990）在首轮请求时合并成第 0 号消息——即标准 OpenAI 规范里的 `role:"system"`。
2. **`systemPromptUpdate: 'in-history'` 路由（DSH 的关键设计）**：每轮请求装配时才求值的 `systemPrompt.context`（如记忆注入，order 900），如果文本**变了**，DSH 不重写头部（重写会把 provider 前缀缓存从第 0 个 token 全部打穿），而是把新文本作为一个**新的独立 system 消息追加在已缓存历史的末尾**。协议形态：

   ```json
   messages = [
     {"role":"system",    "content":"（系统提示词主体…）"},
     {"role":"user",      "content":"今天天气真好"},
     {"role":"assistant", "content":"是呀……"},
     {"role":"system",    "content":"【你记得的事】……"}
   ]
   ```

   注入块还是 system role，只是**位置**排在对话末尾。这就是 fish-memory 注释里「追加在对话末尾防打穿缓存，实测 20 倍成本差」的宿主机制根源。
3. **不支持多 system 消息的路由**：DSH 把变化「归并回首个系统节点」（consolidate into the first system node）——注入体现在头部 system prompt 里，代价是前缀缓存作废。

**成本提醒**：DSH 文档原文提示——`in-history` 路由上，**每个保留的提示词旧版本都会持续计费**，直到压缩将其遮蔽或提示词协调将其清空。注入块每轮换内容，等于历史里躺着一串永不消失的 system 快照。设计注入策略时必须掂量这份成本。

**对小鯨记忆的启示**（挂 03 清单 D2/T2/B6 线）：

- 我们的注入走 context 路线 = **system 消息追加在历史末尾，不是 user**。
- 开场画像注入（B6/D6 的「恒定 100~200 字身份层」）：放头部吃前缀缓存；放末尾追加则每轮多付一份但保住前缀——与 fish-memory 的取舍相同，**位置策略可以照抄它**。
- 顺带推出注入成本的算式：末尾追加路线的每轮额外成本 ≈ 注入块大小 ×（本序列内已保留的注入版本数）。块的体积要小、更新要少（内容不变时 DSH 直接复用前缀，零额外成本）——**「不变化的注入免费，变化的注入按版本数累积付费」**，这是画像层设计「恒定少变」的硬理由。

## Q2 系统节点拆分与 in-history 追加是宿主的还是插件的？插件的"写消息"流程是什么？　`tag: 会话` `tag: 消息` `tag: 注入` `tag: 插件边界`

**问题**（2026-11-12，小主追问）：「把系统提示词拆成一串系统节点放进消息历史」+「system 消息追加在历史末尾，不是 user」这两个机制，是 DSH 自己的还是 dsh-fish-memory 写的？插件写消息的过程是怎样的？

**结论**：**完全是 DSH 宿主的，插件一个字节都没自己"写消息"。** 系统节点拆分、in-history 追加、装配 waterfall、`SystemPromptMessageSource` 节点模型、`SystemPromptUpdate = 'in-history'` 的追加/归并策略、前缀缓存保护——全在宿主 `dsh-agent-loop`（app.asar 内）。插件从头到尾碰不到 messages 数组。

**插件的"写消息"，实际是"递文本"的过程**，五步（行号均为 dsh-fish-memory lib/index.js）：

1. **挂载时登记**（一次性）：`mountFor`（lib/index.js:4277）调用宿主 API `agent.ctx.systemPrompt.context({ name:'memory', order:900, interpolate:false, text })`（lib/index.js:4432-4441）——只登记一个回调，不发消息。同场还登记常驻提醒的 `systemPrompt.section`（order 89990）。`order` 是排序号，决定贡献排在哪个系统节点附近。
2. **每轮请求装配时**：宿主把所有 context/section 贡献按 order 排序，逐个调用 text() 回调。这时插件才干活：选查询词（监听句优先，lib/index.js:4449）→ gate 查问句信息量 → 全库 evaluate 打分 → 分名额/去重/800 字预算 → `render` 产出【你记得的事】文本（lib/index.js:3595）→ **把字符串 return 给宿主**。到此为止，插件没有发任何东西。
3. **宿主接手**：字符串成为一次系统节点贡献。文本没变 → 复用上次节点（前缀缓存零成本）；变了且路由 in-history → 宿主以自己的名义追加 `role:"system"` 消息到历史末尾；路由不支持 → 归并回首节点。
4. **请求后记账**：宿主发 `agent/turn-stopping`，插件监听它，查回复实词重合把 trace 的 assembled 改成 consumed——写的是插件自己的 json 库，与消息流无关。
5. 另一独立通道 `agent/inbox/inserted`（同在 mountFor）只是旁听用户消息，喂说话尺和缓存 lastText，同样不产生消息。

**一句话**：插件是「出题人」，宿主是「排版工」。这个分离是设计得好的地方——小鯨记忆照这个边界来：**自己只算出「该注入什么文本」，位置和缓存策略全交给宿主。**
